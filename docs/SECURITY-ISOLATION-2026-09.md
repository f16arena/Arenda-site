# Изоляция данных: проверка 18.09.2026

Кто что видит и как это гарантируется. Проверялись серверные действия
(`app/actions/*`), маршруты (`app/api/**`), страницы админки и кабинета,
публичные входы и конструктор Building Studio.

## Как устроена изоляция

Данные принадлежат организации по цепочке:

```
Organization → Building → Floor → Space → Tenant → Contract → Charge / Payment
```

- У части моделей есть прямое поле `organizationId` (Building, BuilderProject,
  StoredFile, DocumentTemplate, ApiKey, CashAccount и др.) — фильтр ставится прямо.
- Остальное ограничивается по цепочке (`space: { floor: { buildingId: { in: … } } }`)
  либо проверкой принадлежности из `lib/scope-guards.ts`
  (`assertTenantInOrg`, `assertBuildingInOrg`, `assertSpaceInOrg`, …).
- Сотрудник видит только выданные ему здания: `lib/building-access.ts`
  (`UserBuildingAccess`), без отката «все здания организации».
- Кабинет арендатора грузит данные по `userId` из сессии, а не по параметру из URL.
- Мобильное приложение: `getMobileStaffRequest` (список зданий сотрудника) и
  контекст арендатора; запросы фильтруются этим списком.

## Публичные входы и их ограничители

| Вход | Чем ограничен |
| --- | --- |
| `/showcase/[token]` — 3D-витрина | случайный токен 40 символов, срок 30 дней, отзыв |
| Заявка с витрины (`builder-premise`) | та же проверка ссылки; лимит длины полей |
| Публичная бронь (`createBookingLead`) | rate-limit 3/10 мин, здание проверяется по slug организации |
| Фото помещения (`/api/public/listing-photo`) | только `VACANT` + `RENTABLE`, id — cuid |
| Kaspi webhook | HMAC-подпись, rate-limit, идемпотентность по txnId |
| Приём рыночной статистики | общий секрет в заголовке |
| Cron-маршруты | `authorizeCronRequest` |

## Что изменено в этой проверке

- Ссылка-витрина Building Studio больше не вечная: срок 30 дней (`expires_at`),
  отзыв (`revoked_at`), автор (`created_by_id`). В панели проекта — список
  ссылок с кнопками «Копировать» и «Отозвать».
- Проверка ссылки вынесена в `lib/builder/share-link.ts` и покрыта тестами:
  один и тот же код на витрине и в приёме заявок.
- `npm run security:audit` дополнен правилами по конструктору (проект — только
  в своей организации, витрина уважает отзыв и срок, планы этажей пишутся после
  `assertBuildingInOrg`).
- `scripts/e2e-isolation.ts`: проект чужой организации не читается и не
  изменяется под чужим scope; отозванная и просроченная ссылки не открываются.
- Новый скан `npm run security:scan` — ищет серверные функции, где нет ни
  фильтра по организации, ни проверки принадлежности, ни привязки к сессии.

## Остаточные риски и что стоит сделать дальше

1. **RLS в базе как второй рубеж.** Сейчас изоляция — на уровне приложения
   (Prisma + guards). Политики RLS на таблицах защитили бы и от ошибки в коде.
   Включено пока только для `_prisma_migrations`.
2. **Журнал открытий витрины.** Видно, что ссылка создана и кем, но не видно,
   сколько раз и откуда её открывали.
3. **Внутренние помощники в `lib/`** (`payment-cash`, `tenant-credit`,
   `document-numbering`, …) принимают уже проверенные id. Это верно для всех
   текущих вызывающих (проверено), но гарантируется соглашением, а не типом.
   Стоит завести тип «проверенный id» или передавать orgId внутрь.
4. **Ротация токенов API** (`ApiKey`) и срок их действия — отдельная задача.
